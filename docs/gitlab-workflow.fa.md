# روش کار تیم در GitLab

[English](gitlab-workflow.md)

کار را در یک issue مشخص کنید: چه چیزی باید عوض شود، چه کسی انجامش می‌دهد و از کجا می‌فهمیم تمام شده است. برای شروع، یک کار فعال به هر نفر بدهید. اگر کار بیشتر از یکی دو روز طول می‌کشد، آن را به چند تغییر قابل‌بررسی تقسیم کنید.

## از issue تا مرج

۱. issue را به خودتان اختصاص دهید و برچسب «در حال انجام» بزنید.
۲. از آخرین نسخهٔ main یک شاخه بسازید. مثال زیر شمارهٔ فرضی 123 را به کار می‌برد؛ شمارهٔ issue خودتان را جایگزین کنید.

```bash
git status
git switch main
git pull --ff-only
git switch -c feature/123-short-description
```

اگر تغییر ثبت‌نشده دارید، اول تکلیفش را مشخص کنید؛ pull یا تغییر شاخه نباید کار قبلی‌تان را از بین ببرد.

۳. تغییر را انجام دهید، بررسی‌های مربوط به آن را اجرا کنید و فقط فایل‌های همان کار را stage کنید.

```bash
git diff
git add path/to/changed-file
git diff --cached
git commit -m "Describe the change"
git push -u origin HEAD
glab mr create --draft --template Default
```

مسیر نمونهٔ بالا را با فایل واقعی عوض کنید. برای MR فارسی از Default و برای نسخهٔ انگلیسی از Default.en استفاده کنید. این دستورها در Bash و PowerShell کار می‌کنند.

۴. در MR، نتیجهٔ تغییر و بررسی‌هایی را که انجام داده‌اید بنویسید. اگر issue واقعاً تمام شده، `Closes #123` را در توضیح قرار دهید. برای تغییر ظاهری، تصویر یا ویدئوی کوتاه از دادهٔ آزمایشی بگذارید.
۵. وقتی آمادهٔ بررسی شد، حالت Draft را بردارید، یک reviewer انتخاب کنید و issue را به «منتظر بررسی» ببرید. نفر دیگری می‌تواند بررسی اولیه را انجام دهد؛ مرج نهایی با مسئول پروژه است.
۶. نظرهای باز را پیگیری کنید. بحث را وقتی resolve کنید که تغییر انجام شده یا با reviewer به نتیجه رسیده‌اید. بعد از مرج، شاخهٔ موقت حذف می‌شود؛ issue تکمیل‌شده را ببندید.

## برد و برچسب‌ها

| برچسب | زمان استفاده |
| --- | --- |
| آماده | کار روشن است و می‌توان شروعش کرد. |
| در حال انجام | یک نفر مشغول انجام کار است. |
| منتظر بررسی | MR آماده است و منتظر نظر reviewer هستیم. |
| نیاز به پیگیری | کار به پاسخ، دسترسی یا تصمیم دیگری وابسته است. دلیلش را در issue بنویسید. |

هر issue فقط یکی از سه وضعیت اصلی را داشته باشد. «نیاز به پیگیری» را می‌توان کنار وضعیت فعلی گذاشت. نوع کار را هم با «باگ»، «قابلیت جدید»، «نگهداری» یا «مستندات» مشخص کنید. کار انجام‌شده با بستن issue به ستون Closed می‌رود.

## وقتی گیر می‌کنید

بعد از یک تلاش مشخص، در همان issue بنویسید چه چیزی را امتحان کرده‌اید، چه نتیجه‌ای گرفته‌اید و دقیقاً چه کمکی لازم دارید. خطا را کوتاه و بدون اطلاعات حساس بگذارید. سؤال مبهم «کار نمی‌کند» معمولاً قابل‌پیگیری نیست؛ نسخهٔ ابزار، دستور و متن خطا کمک می‌کنند.

## مرج و انتشار

main شاخهٔ مشترک تیم است. تغییرها از MR وارد آن می‌شوند؛ push مستقیم و force push به آن بسته است. بررسی نهایی و مرج با Maintainer است. موفق‌شدن CI نتیجهٔ بررسی کد است؛ برای انتشار روی سرور، مسئول پروژه باید مرحلهٔ انتشار را جداگانه اجرا و نتیجه را بررسی کند.

کلیدها، رمزها و فایل‌های محیط واقعی از مسیر تعیین‌شدهٔ مسئول پروژه گرفته می‌شوند. آن‌ها را داخل issue، MR، تصویر یا فایل‌های Git نگذارید. برای تست از حساب و دادهٔ آزمایشی استفاده کنید.
